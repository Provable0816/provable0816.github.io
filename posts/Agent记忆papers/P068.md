# P068 Compute or Load KV Cache? Why Not Both?

- 会议/来源：ICML 2025（主会）
- 方向簇：KV
- 链接：https://proceedings.mlr.press/v267/jin25d.html
- 本地全文：cache/txt/P068.txt

## 一句话贡献

提出 Cake：在长上下文在线服务中同时使用**计算与 I/O 两种途径**获取 KV cache。前缀缓存（prefix caching）通过复用已存 KV 避免重复 prefill，但受存储 I/O 带宽限制延迟很高；Cake 用双向调度动态平衡「现算」与「加载」，并加入自适应调度以兼容非前缀缓存请求，相对纯计算与纯 I/O 方法平均把 TTFT 降低 2.6×。

## 1. 问题与第一性原理动机

前缀缓存的收益是显然而又受限于物理的：复用 KV 省下的是算力，付出的是**读带宽**。当存储 I/O 带宽不足时，加载一道 128K 上下文所需的 KV 可能比重新计算还慢；而当 I/O 空闲、算力紧张时，重新计算又成了浪费。这两种资源在时间上此消彼长，因此任何「只用一种途径」的策略都必然在某一侧低效。这是一个典型的双资源调度问题，而不是算法问题：目标不是减少工作量，而是让两类资源同时保持忙碌。

## 2. 核心洞察

洞察是：KV cache 的获取可以被**拆分成若干可并行、可交换次序的片段**——例如按层或按块划分，一部分直接从存储加载、另一部分就地重算，二者并行推进。这样一来，可用带宽与可用 FLOPS 成为同一流水线上的两个可调旋钮，调度的目标变为让二者同时饱和。第二个洞察是调度必须能与非前缀缓存的请求共存：真实服务中总有必须从头 prefill 的请求，若调度器只为缓存命中请求优化，就会在混合负载下劣化，因此需要自适应机制。

## 3. 方法机制

(1) 双向调度：动态决定每个 KV 片段走「加载」还是「重算」，以平衡算力与 I/O；(2) 自适应调度：把非前缀缓存请求纳入同一调度框架，提高整体吞吐并适应资源波动。代价是调度器需要实时掌握带宽与算力的占用情况，调度决策本身有开销，且收益强依赖存储带宽、命中率与请求混合比例——这三点在摘要中未量化。

## 4. 实验证据

跨多种硬件配置、数据集与存储条件评测，相对纯计算方法与纯 I/O 方法平均 TTFT 降低 2.6×。论文强调该结论在不同存储条件下均成立，这一点很重要（避免了只在特定硬件上占优）。

## 5. 第一性原理再审视

第一，2.6× 是相对「仅计算」与「仅 I/O」两个**极端基线**的均值，而实际生产系统通常已经在两者之间做了简单启发式（如阈值切换）；与这些启发式的对比才决定 Cake 的真实增量，摘要未给出。第二，调度类工作的价值体现在**负载极端时的鲁棒性**：当 I/O 高度拥塞或算力被长请求占满时，双向调度是否仍稳定（而非震荡）？这类分析依赖调度算法的稳定性论证或实验，摘要未涉及。第三，「自适应以兼容非前缀缓存请求」涉及公平性问题：优先服务缓存命中请求可提升吞吐却可能让未命中请求饥饿，论文需要给出调度策略的公平性度量。第四，本方法与压缩类方法（P045、P067 等）正交——压缩降低了需要加载/计算的数据量，Cake 改变的是获取方式，二者叠加的收益结构值得研究（压缩后 I/O 变小，调度重心会向计算侧移动）。

## 6. 与相邻工作的关系

与 P044（KVLink，离线预计算文档 KV 供拼接复用）互补：后者关心「如何让 cache 可复用」，Cake 关心「需要时如何最快拿到」；与 P064（HiFC，用 SSD 直连替代 DRAM 换出）同处存储—推理协同设计这一方向，但 HiFC 改变存储介质与路径，Cake 改变调度策略；与 P051（CPU 侧 ANNS 索引）在「把 KV 放在 GPU 之外」这一点上同源，但 Cake 聚焦 prefill 阶段的 KV 获取而非解码期检索。定位上属于面向 serving 的系统优化。

## 7. 可迁移点与开放问题

可迁移：(a) 「同一份结果可以通过多种资源路径获得时，应调度而非二选一」这一原则适用于所有推理系统中的缓存/计算权衡（如推测解码、检索 vs 参数记忆）；(b) 分段并行化是让两种资源同时饱和的通用手段。开放问题：与简单阈值启发式的增益对比；调度算法在资源极端拥塞下的稳定性；缓存命中与未命中请求之间的公平性；与 KV 压缩叠加时的最优分工；以及跨机分布式环境下该调度是否仍成立。
