# P047 MUSTAFAR: Promoting Unstructured Sparsity for KV Cache Pruning in LLM Inference

- 方向簇：KV

## 一句话贡献

证明 KV cache 的**非结构化稀疏**比结构化剪枝更有效：系统探索后发现逐 token 的幅值剪枝对 Key 与 Value 都极为有效，可在不微调、不掉点的情况下达到 70% 稀疏度；配套的 bitmap 稀疏格式与自定义注意力 kernel 能直接在压缩后的 cache 上计算，把 KV cache 压到稠密的 45%，吞吐最高提升 2.23×。

## 1. 问题与第一性原理动机

KV cache 是解码性能的主要瓶颈：上下文一长，每步解码都要把整个 cache 从显存搬进来，注意力因此是访存受限而非算力受限。既有路线分为量化、低秩近似、token 级淘汰与结构化剪枝（如按通道删除）。这些方法共享一个限制：**压缩粒度必须与硬件访问模式对齐**，否则省下的字节无法转化为时间。token 级淘汰删的是整条 KV（粒度粗、信息损失大），结构化剪枝删的是通道（粒度受硬件约束、粒度不够细）。本文的问题设定是：如果允许**任意稀疏模式**（非结构化），并用能直接吃稀疏格式的 kernel，能否在同等精度下拿到更好的压缩？

## 2. 核心洞察

两条经验发现支撑设计。第一，**Key cache 的稀疏性来自离群元素**：key 的分布中存在突出的离群点，逐 token 按幅值剪枝恰好能保留这些关键元素（这与 P049 观察到的 key 通道级离群、P040 观察到的 key 局部同质是同一族现象的两种利用方式）。第二，**Value cache 尽管分布均匀，却同样受益于简单的幅值剪枝**——这一点反直觉（均匀分布通常被认为处处重要），作者把这一现象作为实验结论报告而非理论推导。第三条洞察是工程性的：非结构化稀疏只有在 kernel 能直接对 bitmap 格式计算时才有意义，否则解码期的解压开销会吃掉全部收益，因此 bitmap 格式 + 定制 kernel 是方法不可分割的一部分。

## 3. 方法机制

(1) 剪枝：对 Key 与 Value 分别做逐 token 的幅值剪枝，保留幅值大的元素，形成任意稀疏模式；(2) 存储：用 bitmap 表示稀疏位置，压缩存储；(3) 计算：自定义注意力 kernel 直接在压缩 cache 上完成解码计算，避免先解压再计算。作者报告压缩后 cache 体积降到稠密的 45%，吞吐最高提升 2.23×（相对稠密推理），并强调无需微调。代价是：运行时的剪枝与压缩有开销（论文称之为被 kernel 加速所补偿）；任意稀疏模式对硬件不友好，收益强依赖自定义 kernel 的质量与目标 GPU 架构。

## 4. 实验证据

核心数字：稀疏度最高 70% 而不损失精度、无需微调；KV cache 体积压缩到稠密的 45%；tokens/sec 吞吐最高 2.23×。论文的核心实验是**剪枝策略的系统性对比**，结论是逐 token 幅值剪枝在非结构化设定下优于此前的结构化剪枝方案，且对 Key/Value 均适用。代码开源。

## 5. 第一性原理再审视

第一，「70% 稀疏不掉点」需要明确是在什么任务与什么预算下取得：幅值剪枝保留了分布中的极端值，这类元素往往对应高频/显著 token，因此在常规语言建模与检索任务上表现良好；但在需要精确使用**低幅值**信息的任务（罕见实体、精确计数）上，幅值小并不等于不重要，这类任务最可能暴露剪枝的系统性偏差，而摘要未给出此类评测。第二，2.23× 吞吐与 45% 体积并不成比例，说明加速受限于 kernel 效率与访存模式而非压缩率本身——这提示非结构化稀疏的收益上限由软件栈决定，换架构（如不支持细粒度稀疏的 GPU）可能大幅缩水。第三，论文未报告剪枝与压缩的**运行时开销分解**，而这是「压缩是否真正划算」的关键：若剪枝开销随时长线性增长，在超长上下文下收益会被侵蚀。第四，Value cache 受益于幅值剪枝这一反直觉现象缺少机理解释，只作为经验结论给出；缺少解释意味着难以预测它在其它模型/任务上是否成立。第五，与量化（P034、P048、P049）相比，稀疏与量化是正交的，但二者叠加时的误差是否可加、kernel 能否同时支持稀疏与低比特，论文未涉及。

## 6. 与相邻工作的关系

与 token 级淘汰（SnapKV、H2O）相比，非结构化剪枝在元素粒度上操作、信息损失更细；与结构化剪枝（按通道删除）相比，本文的核心主张正是**放弃结构约束换取更高的有效压缩**；与 P040（AsymKV）都利用了 key 分布的特殊结构，但 AsymKV 做的是合并、本文做的是剪枝；与量化路线（P034/P048/P049）正交可叠加。定位上属于「为稀疏性重做存储格式与 kernel」的系统—算法协同设计这一分支。

## 7. 可迁移点与开放问题

可迁移：(a) 「压缩粒度是否与硬件访问模式匹配」是判断任何压缩方案能否真正提速的第一性检查，比压缩率本身更重要；(b) 为非结构化模式配套 bitmap 格式 + 专用 kernel 的组合，可复用到 MoE 权重稀疏、激活稀疏与梯度稀疏的场景。开放问题：低幅值但关键信息（精确实体/计数）的保持率；剪枝与压缩开销的分解；与量化的联合设计与误差叠加；以及在不同 GPU 架构上收益的可移植性。
